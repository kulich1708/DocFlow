# DocFlow

**DocFlow** — веб-приложение для создания и организации текстовых документов с поддержкой Markdown, черновиков и истории версий. Пользователи могут создавать документы, распределять их по категориям, управлять публичностью, сохранять промежуточные изменения и публиковать именованные версии.

Основная часть проекта — REST API на **C# и ASP.NET Core (.NET 10)**. Backend отвечает за бизнес-логику, хранение данных, аутентификацию, управление документами и версиями, а также предоставляет API-контракт для клиентского приложения.

> **Мой вклад:** backend разработан мной — от моделей предметной области и бизнес-логики до REST API, работы с PostgreSQL, JWT-аутентификации и документации OpenAPI. Frontend создан с помощью Cursor и используется как клиент для взаимодействия с API.

## Возможности

### Документы

- Создание документов с названием, категорией и настройкой публичности.
- Изменение основной информации документа.
- Получение списков документов с учётом публичности и пользовательского контекста.
- Получение документов пользователя и документов выбранной категории.
- Пагинация результатов с настраиваемыми параметрами `Page` и `PageSize`.
- Удаление документов.

### Черновики и версии

- Хранение текущего содержимого документа в отдельном черновике.
- Сохранение изменений черновика и возврат к его исходному содержимому.
- Создание черновика на основе выбранной опубликованной версии.
- Публикация черновика как новой именованной версии документа.
- Хранение содержимого каждой версии независимо от черновика.
- Просмотр, переименование и удаление опубликованных версий.
- Проверка изменений перед публикацией: повторная публикация неизменённого текста не создаёт новую версию.

### Пользователи и аутентификация

- Регистрация и вход по email и паролю.
- Выдача JWT-токена после успешной регистрации или входа.
- Защита операций изменения данных с помощью JWT Bearer-аутентификации.
- Редактирование данных профиля.
- Изменение пароля с проверкой текущего пароля.
- Удаление аккаунта.
- Получение публичной информации профиля и списка документов пользователя.

Пароли хранятся в виде BCrypt-хешей. При удалении аккаунта приватные документы автора удаляются, а публичные документы сохраняются без привязки к пользователю.

### Категории

- Получение списка категорий и их иерархии.
- Получение документов выбранной категории вместе с документами всех вложенных категорий.
- Рекурсивный обход дерева категорий с помощью SQL Common Table Expression (CTE).

### Обработка ошибок и журналирование

- Централизованная обработка исключений через middleware.
- Формирование JSON-ответов с соответствующими HTTP-статусами.
- Запись действий пользователей и ошибок в `activity.log`.
- Разделение событий журнала на уровни `Information`, `Warning` и `Error`.

## Архитектура backend

Backend реализован в рамках одного ASP.NET Core Web API проекта и разделён на функциональные слои.

```text
DocFlow/
├── DocFlow.API/
│   ├── Controllers/          # HTTP endpoints и обработка запросов
│   ├── App/
│   │   ├── DTOs/             # Модели запросов и ответов API
│   │   ├── Mappers/          # Преобразование моделей в DTO
│   │   └── Services/         # Авторизация, пароли, журналирование и др.
│   ├── Models/               # Сущности предметной области
│   ├── Persistence/
│   │   ├── DbContexts/       # EF Core DbContext и конфигурация модели
│   │   └── Repositories/    # Репозитории и Unit of Work
│   ├── Migrations/           # Миграции Entity Framework Core
│   └── Program.cs            # Регистрация зависимостей и настройка приложения
├── client/                   # Клиентское приложение
├── .github/workflows/        # GitHub Actions
└── DocFlow.slnx
```

### Основные компоненты

- **Controllers** — принимают HTTP-запросы, получают параметры и DTO, вызывают необходимые сервисы и репозитории, возвращают HTTP-ответы.
- **DTOs и Mappers** — отделяют внешний контракт API от внутренних сущностей и преобразуют данные для ответов.
- **Models** — содержат сущности предметной области и бизнес-правила. Например, `Document` управляет черновиком и коллекцией версий, а `DocumentVersion` проверяет корректность номера, названия и содержимого версии.
- **Repositories** — инкапсулируют запросы к PostgreSQL и операции чтения/удаления сущностей.
- **UnitOfWork** — предоставляет общий механизм добавления сущностей и сохранения изменений через `AppDbContext`.
- **Services** — отвечают за отдельные задачи: генерацию JWT, хеширование паролей, пагинацию, подготовку DTO и журналирование.
- **GlobalExceptionHandler** — централизованно обрабатывает исключения и формирует ответы API в JSON.

### Работа с данными

Для доступа к PostgreSQL используется Entity Framework Core с провайдером Npgsql. Схема базы данных развивается через EF Core Migrations; миграции автоматически применяются при запуске приложения.

Dapper используется точечно — для рекурсивного SQL-запроса, который получает идентификаторы выбранной категории и всех её потомков. Это позволяет фильтровать документы по всему поддереву категорий.

Для значений `Email` и `DocumentContent` настроены преобразования EF Core. Содержимое черновиков и опубликованных версий хранится в базе данных как текст.

## Модель документов и версий

В основе предметной области лежит сущность `Document`. Она содержит основную информацию документа, черновик и коллекцию опубликованных версий.

- **Document** — название, автор, категория, признак публичности, текущий черновик и список версий.
- **DocumentDraft** — редактируемое содержимое, дата последнего изменения и исходное содержимое, к которому можно сбросить черновик.
- **DocumentVersion** — номер, название и отдельный снимок содержимого на момент публикации.
- **DocumentContent** — типизированная обёртка над текстом документа.

Основной сценарий работы:

1. Пользователь создаёт документ и задаёт его название, категорию и публичность.
2. Backend создаёт начальный черновик, в котором хранится редактируемое Markdown-содержимое.
3. При сохранении черновика обновляется его содержимое и дата изменения.
4. При публикации backend проверяет наличие изменений и создаёт новую именованную версию.
5. Опубликованную версию можно просмотреть, переименовать, удалить или использовать как основу нового черновика.

Каждая опубликованная версия хранит собственное содержимое, поэтому дальнейшее редактирование черновика не изменяет ранее сохранённые версии.

## REST API и Swagger

API организован по контроллерам и доступен по маршруту `/api`. Swagger UI предоставляет интерактивную документацию: отображает endpoints, параметры, DTO и ответы, позволяет отправлять запросы и использовать JWT Bearer-токен для авторизованных методов.

После запуска backend документация доступна по адресу:

```text
https://localhost:7078/swagger
```

### Основные endpoints

#### Account — регистрация и управление аккаунтом

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| `POST` | `/api/Account/register` | Регистрация пользователя и получение JWT |
| `POST` | `/api/Account/login` | Вход в аккаунт и получение JWT |
| `POST` | `/api/Account/logout` | Завершение сеанса на клиенте и запись события в журнал |
| `PUT` | `/api/Account` | Изменение данных профиля |
| `POST` | `/api/Account/change-password` | Изменение пароля |
| `DELETE` | `/api/Account` | Удаление аккаунта |

#### Documents — управление документами

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| `GET` | `/api/Documents` | Получение списка документов с пагинацией |
| `GET` | `/api/Documents/{id}` | Получение документа, черновика и опубликованных версий |
| `POST` | `/api/Documents` | Создание документа |
| `PUT` | `/api/Documents/{id}/general-info` | Изменение названия, категории и публичности |
| `POST` | `/api/Documents/{id}/draft` | Создание черновика на основе выбранной версии |
| `PUT` | `/api/Documents/{id}/draft/save` | Сохранение содержимого черновика |
| `PUT` | `/api/Documents/{id}/draft/reset` | Сброс черновика к исходному содержимому |
| `POST` | `/api/Documents/{id}/versions` | Публикация новой именованной версии |
| `PUT` | `/api/Documents/{documentId}/versions/{versionId}/change-general-info` | Переименование версии |
| `DELETE` | `/api/Documents/{documentId}/versions/{versionId}` | Удаление версии |
| `DELETE` | `/api/Documents/{documentId}` | Удаление документа |

#### Category — категории

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| `GET` | `/api/Category` | Получение списка категорий |
| `GET` | `/api/Category/{id}/documents` | Получение документов категории и её дочерних категорий с пагинацией |

#### Users — профили пользователей

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| `GET` | `/api/Users/{id}` | Получение профиля пользователя |
| `GET` | `/api/Users/{id}/documents` | Получение документов пользователя с пагинацией |

### JWT-аутентификация

Для endpoints, требующих авторизации, клиент передаёт токен в HTTP-заголовке:

```http
Authorization: Bearer <JWT>
```

Swagger настроен с Bearer security scheme и отображает требования авторизации для соответствующих методов на основе атрибутов `[Authorize]`. Это позволяет проверять защищённые endpoints непосредственно из Swagger UI.

### OpenAPI и генерация клиентских методов

OpenAPI-контракт используется не только для документации. На его основе с помощью **Orval** генерируется типизированный API-клиент для frontend:

- OpenAPI-спецификация описывает маршруты, параметры, DTO и ответы backend.
- Orval читает спецификацию из `client/src/api/swagger.json`.
- Генерирует TypeScript-методы и типы в `client/src/api/api-client.ts`.
- Для HTTP-запросов используется Axios с общей конфигурацией из `client/src/api/axios-instance.ts`.

Команда генерации клиента:

```bash
cd client
npm run generate-api
```

Таким образом, Swagger/OpenAPI выступает единым контрактом между серверной частью и клиентом: описание endpoints используется как для ручной проверки API, так и для генерации вызываемых frontend-методов.

## Локальный запуск

### Требования

- .NET SDK 10.
- PostgreSQL.
- Node.js и npm — если требуется запустить клиентское приложение.

### 1. Подготовить базу данных

Создайте базу данных PostgreSQL, например `DocFlow`. Строка подключения задаётся в `DocFlow.API/appsettings.json`.

При запуске backend EF Core автоматически применяет доступные миграции.

### 2. Настроить и запустить backend

Перейдите в каталог `DocFlow.API` и создайте `appsettings.json` на основе шаблона:

```bash
# Linux / macOS
cp appsettings.template.json appsettings.json

# Windows PowerShell
Copy-Item appsettings.template.json appsettings.json
```

Укажите строку подключения PostgreSQL и секретный ключ JWT. Затем выполните:

```bash
dotnet restore
dotnet run --launch-profile https
```

При необходимости доверьте локальный HTTPS-сертификат .NET:

```bash
dotnet dev-certs https --trust
```

Backend будет доступен по адресу `https://localhost:7078`, Swagger UI — по адресу `https://localhost:7078/swagger`.

### 3. Запустить клиентское приложение

В отдельном терминале:

```bash
cd client
npm ci
npm run dev
```

Клиент будет доступен по адресу `http://localhost:5173`.

## Конфигурация

В `DocFlow.API/appsettings.json` используются следующие параметры:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Host=localhost;Port=5432;Database=DocFlow;Username=YOUR_USER;Password=YOUR_PASSWORD"
  },
  "JwtSettings": {
    "SecretKey": "replace-with-a-long-random-secret-key",
    "ExpirationMinutes": 60
  }
}
```

- `ConnectionStrings:DefaultConnection` — параметры подключения к PostgreSQL.
- `JwtSettings:SecretKey` — секретный ключ для подписи JWT.
- `JwtSettings:ExpirationMinutes` — срок действия JWT в минутах.

Для локальной и production-конфигурации используйте собственный секретный ключ и не публикуйте его в репозитории.

## CI/CD

Для проекта настроен GitHub Actions workflow:

- При `push` в `main` и создании `pull request` выполняется сборка backend командой `dotnet build`.
- После успешной сборки при push в `main` запускается `semantic-release` для автоматизации выпуска релиза.
